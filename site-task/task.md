ЗАДАЧА

Создай рабочее веб-приложение — учебную модель предприятия по производству устройств Air (температура + влажность) и Air Plus (температура + влажность + CO₂).

Приложение моделирует складские остатки, резервы, ожидаемые поставки и заказы, позволяет менять данные и задавать вопросы ИИ-аналитику о состоянии склада. ИИ должен отвечать на основе АКТУАЛЬНЫХ данных приложения (не заготовок).

1. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

1.1 Склад и товары

Один склад, два SKU: AIR и AIR\_PLUS.

Для каждого SKU хранить:

физический остаток (physical);

резервы (reserved);

свободный остаток = physical ? reserved (считать, не хранить).

Инварианты (обязательно валидировать):

physical ? 0, reserved ? 0, reserved ? physical;

нельзя повторно зарезервировать одну единицу;

нельзя зарезервировать/отгрузить больше свободного остатка;

одна единица не может быть обещана нескольким заказам.

1.2 Заказы

Активные заказы: id, клиент, SKU, количество, дата создания, срок отгрузки, статус (NEW, RESERVED, SHIPPED), приоритет.

Действия: создать заказ, зарезервировать товар, подтвердить отгрузку.

Показывать: активные заказы, нехватку (shortage) по каждому SKU, риск опоздания (если свободного остатка + ожидаемых поставок до срока не хватает — заказ в зоне риска).

1.3 Поставки (incoming shipments)

Поставки: id, SKU, количество, ожидаемая дата, статус (PLANNED, RECEIVED).

Действие: подтвердить получение (увеличивает physical).

Проверка "что если поставка задержится на N дней":

работает на отдельной копии данных (deep clone / immutable snapshot);

исходное состояние склада не меняется;

выводит список заказов, попавших под угрозу, с причиной и величиной дефицита.

1.4 ИИ-аналитик

Чат-панель, куда пользователь задаёт вопросы о складе.

ИИ формирует ответ на основе сериализованного снимка текущего состояния (остатки, резервы, заказы, поставки, риски), передаваемого в промпт.

Поддержать провайдеров: Anthropic Claude API и OpenAI-совместимый endpoint (ключ из переменной окружения). Если ключа нет — режим "mock-аналитик", который строит ответ детерминированно из данных (без LLM), чтобы приложение оставалось рабочим.

Запрещено использовать заранее заготовленные ответы: ответ должен быть производным от переданного JSON-состояния.

1.5 Производство (дополнительный этап)

Нормативы: на 1 изделие Air/Air Plus требуется N комплектующих (задаётся конфигом), проверка качества — доля брака, рабочее время — часы/смену.

Функция: "можно ли собрать партию X единиц SKU Y к дате D?"

проверяет достаточность комплектующих;

учитывает доступное рабочее время и норму времени на сборку+проверку;

возвращает дату готовности либо причину невозможности.

2. ТЕХНОЛОГИИ И АРХИТЕКТУРА

Стек: TypeScript + React (Vite) для UI, Node.js (Express) для API. Либо единый Next.js (App Router). Выбери один вариант и обоснуй в README.

Хранение: in-memory + JSON-файл (data/seed.json) для персистентности между запусками; запись атомарная.

Домен: чистые функции в src/domain/\* (reserve, ship, receive, shortage, delaySimulation) — без I/O, полностью тестируемые.

API (REST):

GET /api/state — снимок склада, заказов, поставок, рисков;

POST /api/orders — создать заказ;

POST /api/orders/:id/reserve — зарезервировать;

POST /api/orders/:id/ship — отгрузить;

POST /api/shipments/:id/receive — принять поставку;

POST /api/simulate/delay — симуляция задержки (body: {shipmentId, days}), возвращает только результат, состояние не меняет;

POST /api/ai/ask — вопрос ИИ-аналитику.

Конфиг: config/company.json — SKU, BOM, нормы времени, правила риска.

Тесты: vitest — инварианты домена и сценарий задержки (снапшот до/после).

Валидация: zod-схемы на границах API.

UI: одна страница с вкладками: Склад | Заказы | Поставки | Симуляция | ИИ | Производство. Минимальный CSS, читаемые таблицы, кнопки действий, подсветка рисков.

3. ВХОДНЫЕ ДАННЫЕ (архив от компании)

Ожидается архив с:

products.json — товары и BOM;

orders.json — примеры заказов;

stock.json — складские остатки;

incoming.json — ожидаемые поставки;

rules.md — правила (риск опоздания, приоритеты, инварианты);

questions.md — примеры вопросов ИИ-аналитику.

Действия:

Если архив присутствует — прочитать его и преобразовать в data/seed.json через скрипт scripts/import.ts.

Если архива нет — сгенерировать реалистичный seed (10–20 заказов, 3–5 поставок, ненулевые остатки), покрывающий сценарии: дефицит, риск опоздания, успешный резерв.

Не хардкодить данные компании в коде — только через seed/конфиг.

4. ПРАВИЛА И ИНВАРИАНТЫ (жёстко)

Физический остаток включает зарезервированные единицы.

Свободный = физический ? резервы.

Отрицательные значения запрещены на любом шаге.

Повторное списание одной единицы запрещено.

Одна единица не может быть обещана двум заказам.

Симуляция задержки — read-only: результат на копии, оригинал неизменен.

Все действия возвращают новое состояние (или ошибку валидации).

ИИ отвечает только на основе переданного состояния + правил.

6. КРИТЕРИИ ГОТОВНОСТИ (Definition of Done)

npm install && npm run dev поднимает приложение без ошибок.

Видны остатки, резервы, свободный остаток по обоим SKU.

Видны активные заказы, нехватка и риск опоздания.

Работают: создание заказа, резерв, отгрузка, приём поставки.

Невозможны отрицательные остатки и двойное резервирование (тесты это доказывают).

Симуляция задержки не меняет исходное состояние (тест на снапшот).

ИИ-панель отвечает на вопросы, используя текущий JSON-снимок; при отсутствии ключа — работает mock-аналитик.

npm test — зелёный.

README описывает запуск и ограничения.

7. ЧЕГО НЕ ДЕЛАТЬ

Не подключаться к реальным системам предприятия.

Не использовать заранее написанные ответы ИИ.

Не хранить физический и свободный остаток как два независимых поля (свободный всегда вычисляется).

Не мутировать состояние в симуляции задержки.

Не добавлять тяжёлые зависимости без необходимости.

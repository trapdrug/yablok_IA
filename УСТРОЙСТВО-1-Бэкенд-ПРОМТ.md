## 2. Доменные правила (НЕ НАРУШАТЬ — за это снимают баллы)

1. Один склад, два SKU готовой продукции: `FG-AIR`, `FG-PLUS`. Один товар на заказ.
2. `stock.on_hand` = физический остаток, ВКЛЮЧАЕТ зарезервированное.
3. `резерв(sku)` = SUM(`reserved_qty` активных заказов этого sku). `свободно = on_hand - резерв`.
4. По заказу: `осталось отгрузить = quantity - shipped_qty`; `ещё не зарезервировано = quantity - shipped_qty - reserved_qty`.
5. Статусы заказа: `active` открыт, `shipped` исполнен, `cancelled` отменён. Только active требуют товара.
6. Поставка: `expected` ждём, `received` получена. Исторические received и shipped уже учтены в on_hand — не прибавлять повторно.
7. `scenario_now` = 2026-11-02T09:00+03:00 Europe/Moscow. Дату компьютера НЕ использовать. Все сравнения времени — от scenario_now (позже сделай настраиваемым `now`, по умолчанию этот).
8. Просроченная expected-поставка (`expected_at < now` и нет received) — ИСКЛЮЧИТЬ из прогноза до уточнения даты.
9. ЗАПРЕЩЕНО: отрицательные остатки, повторное списание/получение одной партии, обещание одной единицы двум заказам (двойной учёт).
10. Сценарий задержки — ТОЛЬКО на глубокой копии состояния, базу не меняет.
11. Производство (допэтап): одна операция = одно изделие; сборка и тест могут идти параллельно на разных ресурсах; тест изделия только после его сборки + свободного стенда; операция не рвётся на ночь (не влезла до 17:00 → перенос на 09:00 след. раб. дня); за 02-06.11 не влезло → «выход за горизонт»; партия зачисляется целиком после проверки последнего изделия; планирование на копии не списывает компоненты; подтверждённый старт списывает один раз; внешние поставки готовых изделий компоненты не потребляют.

## 3. Алгоритм распределения и готовности (ядро, покрыть тестами)

```
для каждого sku:
  reserved = sum(active.reserved_qty)
  free = on_hand - reserved
  # реальные резервы неприкосновенны
  # остальным активным заказам выделяем free + expected-партии (expected_at >= now, sort by expected_at)
  # заказы сортировать по (due_at, created_at, order_id)
  # каждому заказу нужно need = quantity - shipped_qty - reserved_qty (если <=0 → готов now)
  # идём по заказам по очереди, откусываем от free, затем от ближайших партий
  # готовность заказа = max(now_if_from_stock_or_own_reserve, expected_at использованных партий)
  # если need покрыт не полностью → shortage, readiness = null (дата неизвестна)
  # если readiness > due_at → риск опоздания
```

Эталон на простом примере (должно сойтись 1-в-1):
- ORD-001: 6 Air из своего резерва → 02.11 09:00
- ORD-002: 5 Plus из своего резерва → 02.11 09:00
- ORD-003: 12 свободных Air + 3 из IN-AIR-01 → 03.11 10:00
- ORD-006: 2 из 3 свободных Plus → 02.11 09:00
- ORD-004: 1 свободный Plus + 6 из IN-PLUS-01 → 04.11 09:00
- ORD-005: 7 оставшихся Air из IN-AIR-01 → 03.11 10:00

## 5. API-контракт (ФРОНТЕНД ЗАВЯЗАН НА НЕГО — не меняй имена без нужды)

```
GET  /api/health → {ok:true, now}
GET  /api/snapshot → {now, products[], stock[{sku,on_hand,reserved,free}], orders_active[], shipments_expected[], kpi{...}}
GET  /api/orders?status=active → список заказов с вычисляемыми полями remaining, unreserved, readiness, atRisk, shortage
GET  /api/shipments → все поставки
POST /api/orders {customer, sku, quantity, due_at} → 201 + созданный заказ (reserved_qty=0, shipped_qty=0, status active, id ORD-XXX авто). Валидация: sku существует, quantity>0, due_at>now.
POST /api/orders/{id}/reserve {qty} → reserved_qty+=qty. Отклонить 400 если qty > free(sku) или qty > unreserved заказа.
POST /api/orders/{id}/ship {qty} → on_hand-=qty; reserved_qty-=qty; shipped_qty+=qty; если shipped_qty==quantity → status shipped. Отклонить если qty > reserved_qty заказа, qty > on_hand, заказ не active, повторная отгрузка исполненного.
POST /api/shipments/{id}/receive → on_hand[sku]+=quantity; status received. Повтор → 400 без изменения остатка.
POST /api/scenarios/delay {shipment_id, new_expected_at} → {shipment, before:[{order_id,readiness,atRisk}], after:[...], threatened:[order_id...], explanation} — расчёт НА КОПИИ, БД не меняет. Если shipment received/cancelled/unknown → 404/400 с честным текстом.
GET  /api/production/status → component_stock, incoming, bom
POST /api/production/plan {finished_sku, batch_qty, start_from?=now} → {feasible:bool, shortage:{sku,need,have}[], timeline[{unit, assembly_start,end, test_start,end}], batch_ready_at|null, out_of_horizon:bool, explanation} — на копии, не списывает.
POST /api/production/start {finished_sku, batch_qty} → то же + списание компонентов ОДИН раз (400 если не хватает или уже есть active_batch). Упрощение: достаточно одной активной партии; второй запуск до завершения — отклонить 409.
POST /api/ai/ask {question, scenario?{shipment_id,new_expected_at}} → {answer, facts_used:{snapshot_summary, readiness_table, scenario_diff}} — см. п.6
POST /api/admin/reset?fixture=simple|extended → перезалить БД из 03/04 json (для демо и тестов).
```

Все мутации должны возвращать обновлённый snapshot или затронутые сущности. Все ошибки — JSON `{error, hint}` + понятный русский текст.

## 6. ИИ-аналитик (обязателен, grounded)

- Эндпоинт `/api/ai/ask` собирает: сжатый snapshot (остатки/свободно/резервы), таблицу готовности (order→readiness/atRisk/shortage/почему), выбранный сценарий задержки (если есть), now.
- Системный промт LLM (вшей в `ai.py`):
```
Ты — аналитик цифрового двойника «Сенсорика». Отвечай ТОЛЬКО по переданным facts. Не выдумывай ID, числа, даты, поставки. Если поставки/заказа нет в facts — скажи «такой записи нет». Если нет истории задержек — скажи «истории нет, вероятность оценить нельзя». Всегда называй ID заказов и причину риска (какой партии не хватило). Учитывай aliases товаров (Air=базовый датчик и т.д.). Отвечай по-русски, коротко, по-деловому, с цифрами.
```
- Вызов LLM: OpenAI-compatible `https://www.ai-funpay.ru/v1` (ключ из `opencode.json` → вынеси в `.env`, не коммить ключ в код напрямую, читай из env). Модель по умолчанию `gpt-6-astra`, fallback `deepseek-v4-pro`. Таймаут 30с.
- Fallback без интернета/ключа: детерминированный rule-based ответ (шаблоны: «свободно X, удержано Y для ORD-...», «нужно N, свободно M, ещё K из IN-...», «при задержке пострадают ...») — чтобы демо работало офлайн. В ответе всегда поле `facts_used` для проверки жюри (переформулируй вопрос / измени данные — ответ обновляется).
- Контрольные вопросы (должны отвечать верно):
  1. «На складе 8 Plus. Можно отдать 5 новому клиенту?» → свободно только 3, 5 удержаны для ORD-002.
  2. «Почему ORD-003 пока нельзя отгрузить целиком?» → нужно 15 Air, свободно 12, ещё 3 из IN-AIR-01 (03.11 10:00).
  3. «Какие заказы пострадают при задержке IN-AIR-01 до 05.11?» → ORD-003 и ORD-005, готовность 05.11 10:00, риск опоздания; остальные без изменений; база не тронута.
  4. «Когда придёт IN-UNKNOWN?» → такой записи нет, не выдумывать.
